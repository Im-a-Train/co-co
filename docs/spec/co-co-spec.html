co-co: the Coach Cockpit for eCamp camps

A standalone Tauri desktop app for J+S-Coaches. It signs in to any eCamp v3 instance with your eCamp account and checks camps with a basic set of J+S and PBS rules. Safety concepts and hike plans can be dropped in from Dropbox or network shares. Feedback goes out as eCamp comments or as a ready-to-paste WhatsApp or e-mail message. It has no backend of its own, and personal data never reaches an AI.

Privacy by architecture

Three data zones, enforced in code

Every piece of data carries a zone label from the moment it is loaded. The AI gateway is the only module that can send text to Claude. It refuses red data outright, and it accepts yellow data only after redaction and a preview you confirm. Rules never need names: red-zone data reaches the rule engine only as aggregates such as counts, age bands and yes/no qualification facts.

Green · co-co's own data

  • Rule packs, rule results, category mappings
  • Review status, rounds, snapshot hashes
  • Feedback drafts with no names in them
AI: allowed

Yellow · camp content

  • eCamp program, storyboards, safety considerations
  • Leader names and nicknames (responsibles, collaborators)
  • Dropped documents (safety concepts, hike plans)
AI: only with opt-in, after redaction (names → «Leiter A», phone numbers, e-mail addresses, AHV numbers and addresses removed) and a preview

Red · MiData / NDS (built)

  • Participant lists, birth dates, AHV numbers, health data
  • Leader qualifications with personal details
  • Reduced to aggregates in Rust; only the aggregate is stored, tagged red-derived, and left out of backups by default
AI: never. Only aggregates (e.g. «28 TN, 10–14 J.», «Otter: SLRG Modul See gültig ✓») reach the rule engine.

How it is enforced

Data objects are wrapped as Zoned<T>. The single aiGateway.send() function accepts only green data or yellow data that has been redacted. A lint rule bans imports of the AI client anywhere else.

Documents default to yellow

A safety concept usually contains phone numbers and names. Each document carries the flag «Für KI freigegeben», which is off by default. The text analysis without AI always runs locally.

Secrets

The Claude API key and the eCamp refresh cookies are kept in the OS keychain (Tauri Stronghold or keyring), never in IndexedDB.

Same account, standalone app

How login works without a backend

The flow

  • 1. You choose an instance, e.g. ecamp3.ch. co-co opens that instance's normal login page in a separate Tauri window, so password, PBS MiData, Cevi.DB, Jubla and Google logins all work.
  • 2. After login, co-co reads the JWT cookies (jwt_hp, jwt_s, refresh_token) from that window's cookie store.
  • 3. All API calls go through the Rust side (tauri-plugin-http) with those cookies. Requests leave as first-party requests, so SameSite=strict is not a problem.
  • 4. The token is refreshed through /token/refresh at half its lifetime, as eCamp's own frontend does.

Why not a plain web app?

The eCamp cookies are SameSite=strict and tied to the eCamp host. A web app on another domain would need a proxy server, which is a backend. Tauri avoids that because its native HTTP client is not a browser.

Risk: spike first (M0)

Reading cookies from a Tauri webview depends on the platform and Tauri version. co-co can't run MiData OAuth on its own: eCamp's server is the OAuth client (redirect URI and secret belong to eCamp), so a MiData token alone is useless to the eCamp API. The plan therefore has three levels:

  • Plan A · webview cookies. Read jwt_hp, jwt_s and refresh_token from the login window. Covers every login type.
  • Plan B · intercept the callback. Rust starts GET /auth/pbsmidata and keeps any state cookie. The provider login runs in the webview. Tauri's navigation hook catches the redirect to …/auth/pbsmidata/callback?code&state before it loads, and Rust replays it to eCamp, which answers with Set-Cookie. Covers MiData, Cevi.DB, Jubla and Google without reading webview cookies.
  • Plan C · password only. POST /authentication_token, cookies taken from the response. Doesn't help accounts that only use an OAuth provider.

Plan B open questions: where eCamp keeps the OAuth state (it must be visible to the Rust client), and whether the callback can be stopped before the webview spends the one-time code. M0 decides which plan ships.

eCamp comment caveats

Posting uses POST /comments with the camp and activity IRIs. It works whenever you are an established guest on the camp. Whether leaders see comments depends on the instance's FEATURE_COMMENTS flag, so co-co always offers the clipboard message as well. Comments are limited to 1024 characters; longer items are split or shortened.

Templates (German, i18n)

«Grobprogramm», «Programmbesprechung», «Auflagen», «Nach dem Lagerbesuch», «Abschluss». Each has a WhatsApp variant (*bold*, emoji bullets) and an e-mail variant with a subject line. They live in locales/de/feedback/*.md.

Feedback-Kultur built in

Lob always comes first, «Muss» items cite a rule, and a lint step warns when a «Muss» item contains no question or no next step.

Link to the activity in eCamp ✓

Every activity item in the WhatsApp, e-mail and text message carries the eCamp link of that activity (/camps/{id}/{slug}/program/activity/{activityId}/{scheduleEntryId}/{slug}, eCamp route camp/activity; only the ids matter). The preview has a switch «eCamp-Links einfügen». Each item card has «In eCamp öffnen», which opens the system browser through the Rust command open_ecamp_url (same origin as the session, path below /camps/ only). eCamp comments stay without the link, because they already sit on that activity.

Extraction (local)

PDF via pdf.js, DOCX via mammoth, GPX via DOMParser. Scanned PDFs get optional OCR with tesseract.js. The text and a MiniSearch index are stored in IndexedDB; the original files stay where they are.

Linking

Files are matched to activities by file name, activity title and dates. A confident match is linked automatically; anything else is shown to you as «bestätigen?». A linked document satisfies rules such as «Wanderung hat Detailplan».

Watched folders

Tauri's fs watch API, limited to folders you choose (Tauri capability scope). co-co re-checks a file when its content hash changes, and the camp's rule results update.

export default defineRule(({ facts, params, t }) =>
  facts.days
    .filter(d => !d.isTravelDayPair)

Built · M7 · red zone

MiData connection

MiData (db.scout.ch, PBS's hitobito) knows who is actually in the camp: participants, leaders and their qualifications. co-co uses it read-only to fill the «Lager-Angaben» and to back the rules that today depend on what the coach types in. Personal data stays in a red zone: only counts and yes/no facts reach the app's UI and storage, and nothing from MiData ever reaches the AI.

What the API offers

Verified from db.scout.ch/api/openapi.json (Hitobito JSON:API v1) on 07.11.2026:

  • GET /api/events: filters type, group_id, after_or_on/before_or_on, advisor_id, kind_id; includes dates, kind, contact. Attributes: name, motto, location, description, maximum_participants, advisor_id.
  • GET /api/event_participations with event roles (type, label), so participants and leaders can be told apart.
  • GET /api/people: birthday, gender, nickname, primary group.
  • GET /api/qualifications + qualification_kinds: label, validity, start_at/finish_at per person.
  • Pagination page[number]/page[size], sparse fieldsets fields[...].
  • Auth in the spec: service token (X-TOKEN) or session cookie (_session_id). Per the hitobito docs, OAuth bearer tokens (scopes api, events, people, groups) work as well: access tokens last 2 h, and refresh tokens last 7 days and can be used once.

What it does not offer

  • The PBS camp fields are not in JSON:API v1: coach, expected participants per Stufe, Lagermeldung («camp submitted»), J+S safety flags, canton. Spike M7-0 checks whether the classic JSON export (/groups/{id}/events/{id}.json) exposes them. If not, they stay as coach input.
  • NDS is not in MiData. Registration and closing come from the NDS connection (M8, see below) or stay manual checkboxes.
  • Whether a coach's MiData role may read the participations of a camp they coach is unverified, and the spike checks it.

The link to eCamp already exists

eCamp camps carry hitobitoEventId and hitobitoProvider (set when a camp is created from MiData). co-co uses that link directly. For camps without it, the coach picks the event from /api/events?filter[type][eq]=Event::Camp once per camp. The picker searches camp dates ±14 days across every organisation the MiData account can see, ranks events by overlap with the eCamp dates, shows the organisation, and accepts an event number typed in directly.

Auth option 1: login window (spike first)

Same pattern as the eCamp login that already works: open the db.scout.ch login in a separate Tauri window, take the session cookie into the Rust side, and call the JSON:API from there. The spec lists session auth, and no app registration is needed. Open questions: how long the session lasts, and whether PBS is fine with this use.

Auth option 2: official OAuth app

The clean long-term route, but a PBS Bundesebene admin must register the app. The hitobito docs require https redirect URIs on production (no localhost loopback) and don't mention PKCE. A client secret can't be kept secret in a desktop binary. Needs a conversation with PBS: a public client, a loopback exception, or a tiny redirect relay.

Auth option 3: service token (pilot)

An Abteilung or Kantonalverband admin creates a read-only X-TOKEN (people, events and participants for that layer and below). The coach pastes it once, and co-co stores it in the OS keychain. Good for a pilot, but the token isn't tied to one person, so whoever issues it carries the data-protection responsibility.

Red-zone architecture

  • Its own Rust module midata, with its own HTTP client and its own cookie/token store in the keychain, separate from eCamp.
  • Raw responses are parsed and reduced in Rust. Only a MidataAggregate crosses to the UI: participant count, min/max age, count per age band, leaders as nickname + qualification yes/no, coach match, and a «Stand MiData» timestamp.
  • IndexedDB keeps only the aggregate, tagged red-derived. The AI gateway refuses it, and a backup export can leave it out.
  • Refreshed only when the coach asks, never in the background.

In the app

  • Lager-Angaben gets an «Aus MiData übernehmen» button. It shows, field by field, the MiData value next to the current one, and the coach accepts each field. Accepted fields get a small «MiData» badge.
  • Rules JS-CAMP-02, JS-LL-01, BP-WOLF-01 and BP-WATER-01 then rely on the MiData facts, and the finding says «Quelle: MiData, Stand …».
  • A qualification matrix (leaders × required qualifications for the camp's safety-relevant activities) replaces typing them in by hand. «Qualifikationsarten aus MiData» lists every qualification label found (valid / expired) and lets the coach map unknown labels to a column; a warning appears when MiData does not allow reading qualifications.
  • Safety-relevant activities come from keyword detection in title, location, storyboard and safety text (the SAFE-WATER-01 / SAFE-MTN-01 keyword lists plus a winter list); each activity shows the matching keywords, and a wrong area can be dismissed per camp.
  • Coach: PBS stores the camp coach as the restricted role Event::Camp::Role::Coach; co-co shows «Coach laut MiData» and checks it against your MiData person number, detected from the login URL when possible.
  • No double login: when you sign in to eCamp via MiData OAuth, co-co adopts the MiData session from the same login window. Password or Google logins to eCamp still need a separate MiData login.
Built · M8 · red zone

NDS connection

NDS (Nationale Datenbank Sport) knows what BASPO sees: whether the camp is registered and approved, planned and actual numbers, which activities still need an attendance check, and the rental-material order. It has no public API, so co-co reads the NDS web app's own endpoints, read-only, with the coach's AGOV login. Only states, dates and counts reach the UI; names, birth dates, AHV numbers and addresses never leave Rust, and nothing from NDS reaches the AI. See ADR 0007.

What co-co reads

Reverse-engineered from redacted browser captures (structure only, no personal data); spec in docs/contracts/nds-api/:

  • Login: AGOV → Keycloak (/perorgfin/oauth2/authorization/keycloak) → SESSION cookie, kept in the OS keychain.
  • GraphQL POST /youthtraining/graphql/admin: OfferList, CampList, ActivityListForCamp; supervisor/participant lists requested with IDs and roles only, to count them.
  • REST /youthtraining/offer/camp/{id}/details and /statistics (planned vs. actual counts), offer details, rental orders (/material/graphql/admin).
  • Only queries; anything that is not a GraphQL query is rejected in Rust.

Caveats

  • Unofficial. The web API can change without notice; the settings diagnosis shows which endpoints and fields still answer. Using it outside the NDS website may conflict with the NDS terms of use; ask BASPO before a release.
  • The official partner «Standard-API» (api.baspo.admin.ch/nds/api) only covers Kaderbildung and needs a partnership contract, so it doesn't help camps.
  • Only a few state codes are known. Suggestions come only from known codes; unknown codes are shown raw. The code for «attendance check open» is still inferred.

Open points and risks

Login spike ✓

Resolved 07.11.2026 on Windows 11 with Plan A: PBS MiData login in the Tauri window works and the HttpOnly cookies are readable. macOS and Linux are still to be tried; Plan B and Plan C stay as fallbacks there.

Comments visible ✓

Yes: app.ecamp3.ch has FEATURE_COMMENTS enabled. Posting and deleting a comment was verified on dev.ecamp3.ch.

MiData query syntax ✓

Checked 07.11.2026 against db.scout.ch/api/openapi.json: filters need the operator (filter[after_or_on][eq]), events only allow include=dates|kind|contact|… (organisation names via /api/groups), participations link people via participant. Unknown names return HTTP 400; a unit test now pins every query to the spec. See docs/contracts/midata-api.md.

eCamp links: live check

The activity link and «In eCamp öffnen» (tauri-plugin-opener) are tested with mocks only. Try them once in the release exe against app.ecamp3.ch. The slug segments only approximate eCamp's own shorteners (shortTitle or the first 16 characters of the title), which is harmless because eCamp resolves the ids only.

Cross-source rules: tuning

CMP-CON-* are new and run as «Hinweis» or «Soll» only. Open: which eCamp collaborators count as «Leitende» (CON-02 counts established members and managers), name matching by nickname (CON-03, can give false hits), and whether NDS «planned» counts are the right basis. Check them against 2–3 real camps.

More checks, more data

Not built yet, because the meaning or the data is missing:

  • NDS children/adolescents vs. MiData age bands: which age limits NDS uses
  • NDS campAgendaUploaded and coachAuthorizedForContribution: deadline and meaning unclear
  • A winter check like SAFE-MTN-03: needs a winter keyword list in the rule pack
  • NDS activity location/time, NDS coach, J+S numbers: not fetched (red zone); possible later as Rust-side yes/no facts

Rule confirmation

The leader ratio, the training-free days and the 2027 Bewegungszeit stay «Soll / Quelle unsicher» until PBS or BASPO confirms them.

IndexedDB durability

The webview's storage can be wiped by an uninstall or a profile reset. co-co reminds you to export a backup after each review round.

OAuth callback

eCamp does not validate the callback URL (a possible open redirect). Report it to the eCamp team; co-co doesn't rely on it.
